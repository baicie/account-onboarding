## 8. 本门禁发现并修复的集成缺陷（真实夹具才暴露）

这一节是 R2 的核心价值：只有把真实 Keycloak + Mailpit 接进引擎后才暴露的问题，均已修复并在
`go test ./... -race -count=1`（exit 0）下回归。

1. **Mailpit 单封邮件详情端点/时间字段错误** — `internal/provider/mailbox/mailpit/mailpit.go`
   - `GET /api/v1/messages/{id}` 在真实 Mailpit v1.32 返回 404；正确端点是单数 `GET /api/v1/message/{id}`。
   - 详情载荷的时间字段是 `Date`（列表是 `Created`）；此前 hydrated message 的 `ReceivedAt` 为零值，
     `mailx` 时间窗拒收，表现为永远 `WAITING_EMAIL`。
   - 修复：`get` 路径改为单数端点 + `Created`→`Date` 回退；包内单测同步更新。
2. **列表响应只有元数据，引擎未取正文** — `internal/workflow/steps.go`（`stepWaitEmail`）
   - Mailpit（以及部分 Cloudflare 部署）列表接口不含正文，`Message.Text/HTML` 为空，`mailx` 永远提取不到链接。
   - 修复：对未消费且正文为空的候选通过 `GetMessage` 补水（每 tick 上限 50 封），`ClassNotFound` 跳过，
     其他错误按类别上抛；新增 DEBUG 级 `wait_email scan` 计数日志（不含正文/链接）。
3. **Keycloak 26 的 Secure 会话 Cookie 在 http loopback 被 Go cookiejar 丢弃** —
   `internal/provider/keycloak/keycloak.go` + `jar_test.go`
   - Keycloak 26 即使对 http loopback 也给 `AUTH_SESSION_ID`/`KC_AUTH_SESSION_HASH` 加 `Secure`；
     Go `cookiejar` 拒绝在 http 上回送 → 两步验证 GET 与登录表单 POST 丢失会话。
   - 修复：新增沙箱专用 `loopbackSecureJar`（仍受 adapter 的 loopback base-URL 门禁约束），
     只对 loopback 放行 Secure cookie；单测覆盖。修复后 `ConfirmEmail` 在真实夹具上返回 `VERIFIED`。
4. 门禁自身（非产品代码）修正：E2E 轮询改为 `GET /v1/runs` 单次列表并在受控环境放宽
   `ONBOARD_RATE_LIMIT_PER_MINUTE`（API 新增了 300 req/min 限流）；测试侧 Admin REST 的
   client_credentials 必须用 `moonbyte-test` realm 的 token 端点（`master` 不识别该客户端）；
   Mailpit 无单封 DELETE 路由，teardown 改用文档规定的批量 `DELETE /api/v1/messages {"IDs":[...]}`。

> 迭代历史（诚实记录）：首轮 5 个 run 在 `request_verification` 以 `NOT_AUTHORIZED` 失败，根因是
> client_credentials 打到了 master realm（已修）；随后 5 个 run 稳定停在 `WAITING_EMAIL`，由上述
> 1/2/3 三个缺陷共同造成；修复后同一门禁 5/5 PASS（先 5.6s，后 0.8–1.7s）。没有把失败轮次伪装成 PASS，
> 失败轮次的 `state.sqlite` 与日志仍保留在 `.sandbox/e2e/`。

     失败时能落成错误类别而不是截图。真实浏览器 UI 自动化未执行，浏览器端渲染/JS 交互未验证。

## 11. Provider 契约与错误映射证据（unit/contract）

`go test ./internal/provider/keycloak -race -count=1 -cover` → **exit 0，coverage 72.6%，27 个顶层测试全 PASS**，
其中覆盖任务要求的全部要点：

- descriptor：三个 wrapper 的 `kind`（identity/sandbox/credential）、`name=keycloak-test`、`contract_version=v1`、
  `enabled=true`、`live=false`、capabilities；`NewDisabled` 时 `enabled=false` 且调用在**任何网络请求前**
  返回 `NOT_AUTHORIZED`（禁用适配器 + 无服务端 = 零请求证据）。
- admin token：password grant 与 client_credentials 两条路径；缓存到 `expiry-30s`（60s token → 1 次请求；
  推进 31s 后重新获取）；client_credentials 走 realm token 端点（不是 master）；401 只做一次 token 刷新重试，403 不重试。
- 用户创建幂等：`409` → 重新精确查找并复用；同一 subject 两次 Register → 同一 subject id、1 个用户、1 次创建。
- 发验证邮件：`PUT execute-actions-email`，body `["VERIFY_EMAIL"]`，带 `client_id`/`lifespan`（默认 3600s）。
- 已认证用户：`CheckVerification` 读 `emailVerified`；`RequestVerification` 对已验证身份不发第二封邮件。
- 两步确认：GET action-token → 解析 “Click here to proceed” → 只跟随同源 action-token 链接 → Admin API 二次确认；
  过期 interstitial → `VerificationExpired`；410 → `AUTH_EXPIRED`；异源/非 action-token/非 loopback 链接 →
  `VALIDATION` 且**零 HTTP 请求**（SSRF 门禁）。
- 完整 PKCE：fake OP 端点上授权 → 登录 → code → token（校验 verifier/challenge 哈希、redirect、client_id）→
  id_token nonce/aud/exp → userinfo；token 只写入 `secret://keycloak_oidc/<random>`（kind 与 ref kind 一致），
  返回 DTO 仅含 `issuer/subject/audience/expires_at`；错误 verifier 被 OP 拒绝 → `AUTH_EXPIRED`。
- 凭据验证：有效 → `VALID`；401 且已过期 → `EXPIRED`；401 未过期 → `INVALID`；subject 不匹配 → `INVALID`；
  外来 ref kind → `VALIDATION`。

  超时 → `TIMEOUT_UNCERTAIN`；非 JSON → `PROVIDER_BUG`；跨域重定向 → `PROVIDER_BUG`；410 → `AUTH_EXPIRED`；
  base URL 非 loopback、URL 内嵌凭据、query/fragment、http 未显式放行、非法 realm/client/redirect → `VALIDATION`。
- 秘密不泄漏：上游 400 body 中注入 `SUPER-SECRET-TOKEN-VALUE` 后错误字符串不含该值；成功 DTO 序列化不含
  access token、也不含 `secret://` 引用。
