one file (this report).

### P1-1 (blocking)

`scripts/materialize_secrets.sh:125-151` - `recover_transaction` replays an
unauthenticated journal with an unvalidated `name` field.

- `:129` reads "kind name sum"; the charset restriction `[A-Za-z0-9_.-]` is applied
  only to SOURCE names (`:195-198`), never on replay, so "../" passes into rm/mv.
- `:132` "verifies" the record with sha256("kind name") truncated to 16 hex - public
  text, recomputable by anyone.
- `:146` executes `rm -f -- "$DST/$name"`; `:141` executes
  `mv -f -- "$BAK/$name" "$DST/$name"`.
- Executed proof: planting `I ../victimdir/canary 684a33636cf12a04` in
  `<target>/.materialize.txn/journal` and tracing the next run shows
  `rm -f -- /tmp/.../dst/../victimdir/canary`, and the canary was deleted. The
  target is chowned to the runtime UID by the script itself (`:94`/`:262` with
  `--uid/--gid`, exactly how `tests/r22/arm64_full.sh:125` calls it) and the init
  container runs as root with `DAC_OVERRIDE`, so a compromised service process can
  delete arbitrary root-owned files on the next start, e.g. `/app/data/state.sqlite`.
  Fix is one validation on replay.

### P1-2 (blocking)

`internal/ops/retention.go:223-239` - `-purge-invalid` has no floor; executed
repro: 2 unverifiable snapshots -> `kept=0 deleted=2`, only the retention report
left. The valid-backup path IS safe (mtime-prefix keep + `MinValid>=1` floor, 8/8
tests pass), so "cannot delete the last VALID backup" is true; "cannot destroy the
whole recovery set" is false.

### P2 must fix before v0.1

- **P2-1** the materializer moves the live file aside before renaming in
  (`:249` then `:252`) so the name is briefly absent - contradicts the stated
  guarantee.
- **P2-2** `restore.go:213/234` - a SIGKILL between the two renames leaves no
  database, and `storage.Open` (`store.go:98-118`) silently CREATES an empty
  schema-6 database that then reports ready.
- **P2-3** `drained:true` counts HTTP writes only; an in-flight `Tick` still commits
  via `engine.go:363`.
- **P2-4** a secret removed from the source set is never deleted from the target,
  contradicting the script's stated contract (disclosed in the RC record).
- **P2-5** `running_restore.sh:177` can SKIP the disk-full case while the CI job
  title advertises it as covered.

### P2 defer to v0.2

- **P2-6** a partially failed delete is reported as `keep` and counted as kept.
- **P2-7** the trusted-CI gate record does not pin the branch or the workflow content.
- **P2-8** `PROVENANCE_VERIFIED` reads the source identity from self-declared build
  args.

P3: 8 recorded items, no work implied (the reviewer's item list is summarised in its
own words as "recorded, no work implied"; the incident removed the verbatim list).

### What the reviewer confirmed as sound (so it need not be re-litigated)

Background executors are all paused (only the worker loop and the 30s sweeper exist;
both gated); maintenance endpoints require the admin token plus CSRF; the gate now
sits inside the rate limiter; restore fsyncs every staged write before rename and
fails closed on wrong key / tamper / missing manifest; the arm64 checks really
execute in an aarch64 container; the schema5 database really comes from the
historical binary (verified `3796047` is an ancestor carrying migration 0005 and not
0006); `TRUSTED_BUILD_VERIFIED` is hard-coded false, the verifier's 15 negative
tests pass, and missing attestation / wrong subject / forged statement are
genuinely rejected.

### A hypothesis the reviewer raised and then refuted

It suspected `.github/workflows/r22-provenance.yml:29` used a BRE grep
(`pass=[0-9]+` would never match); it verifies the line is `grep -qE`, so there
is no defect. Recorded so it is not re-litigated.

### What the reviewer could not verify

Anything docker/kind/buildx (no daemon) - arm64, `docker_secret`, `kind_secret` and
`buildkit_provenance` were reviewed as source only; no GitHub API check of the quoted
run IDs; no `go test -race`; no SIGKILL injection into restore (P2-2 is derived from
the code, not a crash test); the macOS materializer reproduction needed a no-op
`flock` shim because macOS has none, and the shim is not on the replayed path.

## 4. Decision

**`V0.1_SANDBOX_RC_REVIEW_BLOCKED`.** Two P1 findings block acceptance. Both are
small and local; neither requires a redesign. The freeze was **not** lifted and no
product code was changed: the fix needs explicit operator authorization.

Minimal fix scope if authorized:

1. **P1-1** - validate the replayed `name` in `recover_transaction` against
   `[A-Za-z0-9_.-]` and skip any record that fails; keep the checksum as a torn-line
   guard, not as authentication; apply the same validation when writing records. About
   4 lines plus one regression case in `tests/r22/materializer_fault.sh`.
2. **P1-2** - apply the `MinValid` floor to **all** retention candidates, not only the
   valid prefix, so `-purge-invalid` can never empty the directory; report instead of
   deleting when nothing verifies. About 6 lines plus two unit tests.
3. Optional, same round if the operator wants the reviewer's five must-fix P2s:
   P2-1 (name-absent window), P2-2 (empty schema-6 database after a crash in the
   publish window), P2-3 (drain counts HTTP writes only), P2-4 (removed secret never
   deleted), P2-5 (disk-full can SKIP in CI).

Re-freeze judgement: **yes**, fixes 1 and 2 change product code. The new freeze point
must re-run `ci`, `r22-deployment-matrix` (`materializer-faults` and
`running-restore` cover both) and `r22-arm64-full` (its test image bakes the
materializer); `r16-sandbox-e2e` and `supply-chain` trigger automatically.
`r22-provenance` stays a v0.2 item either way. The main integration plan stays
technically valid but **must not be executed** until the fix is merged and re-frozen.
