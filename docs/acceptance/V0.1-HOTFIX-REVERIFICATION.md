## 3. New findings in this scope (not P0/P1)

- **P2 (documentation/semantics, N-3)** — `--revoke` does not suppress the normal install pass:
  `scripts/materialize_secrets.sh:310-322` runs the revoke loop and `:323-337` then installs the
  whole source set, so revoking a name that is **still present in `--source-dir`** silently
  re-installs it in the same run (probe: `--revoke keep` with `src/keep` present → `keep` is back
  with the source content, `rc=0`). `deploy/secret-materializer/README.md:59-70` says the operation
  "removes only that name" but never says the source set is re-materialized in the same invocation.
  No data loss and no privilege gained, but a revocation the operator believes succeeded can leave
  the credential live. One sentence in the README (drop the name from the source first) or a hard
  error when a `--revoke` name is also staged would close it.
- **P3 (N-6 residual)** — after the publish succeeds, two early returns do **not** clear the marker:
  `internal/ops/restore.go:262-264` (chmod) and `:265-267` (dir sync). Both are fail-closed and
  cannot be confused with a first install (the database exists, so `store.go:106` lets the service
  open it), but the stale marker blocks the *next* `restore` until an operator removes it by hand
  (`restore.go:385-388`). Same for a marker left by a `Fprintf`/`Sync` failure at `:390-399`.
  `docs/runbooks/BACKUP-RESTORE.md` has no section telling an operator what the marker is or that
  removing it is the recovery step; the only guidance is inside two error strings.
- **P3 (cosmetic)** — `deploy/secret-materializer/README.md:70-71`: the new section's last line is
  followed immediately by `## Kubernetes projected volumes` with no blank line (renders correctly
  under CommonMark, but it is a markdown-lint wart).
- **P3 (cosmetic)** — a revoke-only run reports `materialized 0 secret file(s)`
  (`scripts/materialize_secrets.sh:347`), which reads oddly for an invocation whose only effect was
  a removal.
- **Observation, not a finding** — `internal/storage/store.go:108` probes the marker with
  `os.Stat` (follows symlinks) while `writeRestoreMarker` refuses with `O_EXCL`: a *dangling*
  symlink planted at the marker path disables the open-time guard. This is not an escalation,
  because anyone able to plant it can simply delete the marker, but `os.Lstat` would make the two
  checks agree.

## 4. What I could not verify

- **The pre-fix N-3 failure itself.** The bug is GNU `mv` refusing `mv -f a b` when `a` and `b` are
  two links to one inode; macOS/BSD `mv` returns 0 for that case (probe 14), so the pre-fix script
  also "passes" my mid-revoke probe here (probe 9). What I did verify is that the fixed code takes
  the new `[ -ef ]` branch (probe 10) and recovers correctly; the Linux-side improvement is
  reasoned from `scripts/materialize_secrets.sh:195-203`, not executed.
- **The disk-full branch as a real event.** No root-on-Linux with tmpfs mount available, so
  `running_restore.sh:171-177` was not executed; my N-2 evidence is the control flow plus the
  anchored-grep behaviour on a synthesized skip log, not a green/run of that branch.
- **The privileged/deployment paths** (`sudo env R22_BIN_DIR=…`, the CI matrix itself) — not run
  here; no docker/kind per the brief.
- **Post-publish `chmod`/`syncDir` failure injection** inside `Restore` — no seam exists for those
  two errors, so their marker-left-behind behaviour is read from `:262-267`, not executed.
