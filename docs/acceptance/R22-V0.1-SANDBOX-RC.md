## 2. What this RC is

A single-node operator control plane for account onboarding:

- Go HTTP service, SQLite (WAL) schema 6, durable workflow with leases/fencing.
- Console UI: runs (filters, cursor paging, detail, steps, events, resume,
  cancel), external operations (filters, detail, audit, resolve with expected
  version), alerts/durable outbox (reconcile, dispatch, resolve, re-arm, delivery
  history).
- Session/CSRF/RBAC, AES-256-GCM secrets, encrypted backup/restore, retention.
- Planned-maintenance window and the running-restore protocol.
- Container image (non-root 10001, read-only rootfs) plus compose + Kubernetes
  manifests, secret materializer, loopback TLS staging stack.
- Fake providers for sandbox work; real Cloudflare/GitHub/WorkBuddy providers stay
  disabled (no authorization for live calls).

## 4. Deferred to v0.2 (explicitly out of v0.1 scope)

1. Advanced browser matrix: session expiry/revocation/read-only role, real
   Keycloak/Mailpit browser path, full alerts/external-operation browser matrix.
2. Full trusted SLSA: signature, issuer, signing identity against a trust root;
   `TRUSTED_BUILD_VERIFIED` stays unclaimed until then.
3. GitHub protected workflow definition (ruleset, required checks, environment
   approval) - administrator action.
4. Real external platform validation (Cloudflare stage A/B, GitHub account,
   WorkBuddy) and any formal GHCR publish, tag, release, merge or deployment.
5. Retention/integration hardening listed as P3 in `REVIEW-R22-M3.md` and below.

## 5. Known limitations of this RC

Operational:

- Single node, single SQLite file. No HA, no leader election, no horizontal scale.
- Completing a restore needs the documented maintenance window **and a restart**;
  the maintenance flag is process local by design so a crash cannot leave the
  service "stuck in maintenance".
- `/readyz` requires the admin bearer token, so a probe or load balancer needs
  one; `/healthz` stays public (liveness).
- The admin token is a single shared credential (the viewer token is separate);
  there is no per-operator account model.
- Secrets are materialized by an init container that needs root with
  `CHOWN`/`DAC_OVERRIDE`/`FOWNER`; the no-root alternative needs a stricter
  mount contract (recorded in `REVIEW-R22-M3.md`).
- A secret name removed from the source set is **not** deleted from the target;
  removing a secret is an explicit operator step.

Correctness / coverage:

- SIGKILL in the middle of `restore` has no deterministic injection point, so
  that window is reasoned about, not tested.
- Disk-full coverage requires root + tmpfs (Linux CI), not a developer laptop.
- Browser coverage is the 14-test admin core; the advanced matrix is v0.2.
- Retention assumes the snapshot directory is operator-owned and private; it does
  not defend against a local attacker who can already write there.

## 6. Review status

A self-review of `788197a..7f7c3da` was performed (documented per finding in the
commit messages and in `REVIEW-R22-M3.md`). It found and fixed five real
defects:

1. a committed `.pyc` build artifact (untracked, `__pycache__/` ignored);
2. the maintenance window paused the workers but not the deadline sweeper, which
   kept mutating run state while the service claimed to be quiesced;
3. the maintenance gate sat outside the rate limiter, so rejected traffic
   bypassed rate limiting;
4. the provenance verifier compared the attestation subject against the index
   digest instead of the platform manifest digest;
5. a verifier flag the acceptance script used was never registered in argparse.

**This is not an independent review.** No second reviewer was available in this
session, so `INDEPENDENT_REVIEW_PENDING` stands: the v0.1 RC may be used in a
sandbox, but a release decision needs an independent reviewer to read
`788197a..HEAD` (materializer, maintenance/restore, retention, provenance
verifier, arm64 and historical harnesses).

## 7. PR integration plan (real, not proposed-in-the-abstract)

Facts measured from the current repository state:

- The stack is **linear**: 16 branches (R8 -> R22), each one contains its parent
  head, `behind=0` everywhere, main is still `9726fc1` and 177 commits behind the tip.
- Merging the branches in order in an isolated worktree: **16/16 merges, 0
  conflicts, 0 unmerged paths**, and the merged tree equals the tip tree
  (evidence `docs/acceptance/evidence/r22/merge-dryrun.txt`).
- A **squash** of the whole stack onto main also produces exactly the same tree
  with 0 conflicts (`git merge --squash` dry run, tree `bbbb5101ee085e26b4fd0bf54ce85b03160715f7`
  equals the tip tree at simulation time).

Consequences for the operator:

1. Recommended integration: merge PR #16 (which already contains the whole
   linear stack) into main. Either "create a merge commit" (keeps the audit trail
   of 16 branches) or "squash" (linear history) works; both yield the same tree.
   Do not merge the intermediate PRs one by one unless the audit trail per PR is
   required - it is 16 identical outcomes.
2. **The new main commit SHA will differ** from the frozen `7f7c3da`. The tree is
   identical, so build inputs are identical, but any release artifact must be
   rebuilt and re-bound to the merged SHA, and the approval must name that SHA.
3. Never reuse an approval or a candidate digest bound to `7f7c3da` for a merged
   SHA. Re-run the preflight after the merge.

## 8. How to run the RC (sandbox)

    make verify                                     # build, vet, race tests
    bash tests/sandbox/verify.sh                     # sandbox infra checks
    ONBOARD_SANDBOX_E2E=1 go test ./tests/e2e -v     # real Keycloak + Mailpit E2E
    bash tests/browser/run.sh                        # 14-test admin core
    bash tests/r22/docker_secret.sh                  # secret projection in a container
    bash tests/r22/kind_secret.sh                    # projected Secret + rotation
    bash tests/r22/running_restore.sh                # maintenance + restore + retention
    bash scripts/r22_merge_dryrun.sh                 # integration dry run
