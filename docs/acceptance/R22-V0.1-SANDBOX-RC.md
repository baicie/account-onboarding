## 2. What the RC is

A single-node operator control plane for account onboarding: Go HTTP service,
SQLite WAL schema 6, durable workflow with leases/fencing, console UI (runs,
external operations, alerts/outbox), session/CSRF/RBAC, AES-256-GCM secrets,
encrypted backup/restore with retention, a planned-maintenance window with a
documented running-restore protocol, container image (non-root 10001, read-only
rootfs), compose + Kubernetes manifests, secret materializer and a loopback-TLS
staging stack. Providers are the sandbox fakes; real Cloudflare/GitHub/WorkBuddy
providers stay disabled (no authorization for live calls).

## 4. Deferred to v0.2 (explicitly out of v0.1 scope)

### 4.1 BuildKit / SLSA - real finding, not a parser accident

The attested build itself works: BuildKit produces the platform manifest, the
attestation manifest, a SLSA statement and an SPDX SBOM, and all 16 negative
checks pass (wrong commit/repository/platform/subject, forged statement fetched
from the registry, image built without attestations, rebuild is a different
artifact).

What cannot be verified for this build mode is the **source identity**: for a
local-directory build BuildKit records no git material (the only dependency in
the real statement was the SBOM scanner image,
`pkg:docker/docker/buildkit-syft-scanner@stable-1`) and it does not expose
`SOURCE_COMMIT`/`SOURCE_REPOSITORY` where the verifier can reach them. So the statement
binds subject, builder, invocation and platform, but **not** the git commit.
Verifying source identity needs a different build mode (a git context build, or a
signed attestation whose predicate carries the source), which is a v0.2 change.
`TRUSTED_BUILD_VERIFIED` stays unclaimed either way.

### 4.2 Other v0.2 items

1. Advanced browser matrix (session expiry/revocation/read-only, real
   Keycloak/Mailpit browser path, full alerts and external-operation matrix).
2. Trusted SLSA: signature, issuer and signing identity against a trust root.
3. GitHub protected workflow definition (ruleset, required checks, environment
   approval) - administrator action, cannot be self-granted.
4. Real platform validation (Cloudflare stage A/B, GitHub account, WorkBuddy) and
   any formal GHCR publish, tag, release, merge or deployment.
5. Retention/restore hardening listed as P3 in `REVIEW-R22-M3.md` and below.

## 5. Known limitations of this RC

Operational:

- Single node, single SQLite file: no HA, no leader election, no horizontal scale.
- Completing a restore needs the documented maintenance window **and a restart**;
  the maintenance flag is process local by design, so a crash can never leave the
  service stuck in maintenance against a half-replaced database.
- `/readyz` requires the admin bearer token (a probe needs one); `/healthz` is
  public and stays 200 during maintenance (liveness).
- The admin token is a single shared credential; the viewer token is separate.
  There is no per-operator account model.
- The secret materializer init container needs root with
  `CHOWN`/`DAC_OVERRIDE`/`FOWNER`. The no-root alternative requires a stricter
  mount contract (recorded in `REVIEW-R22-M3.md`).
- A secret name removed from the source set is not deleted from the target;
  removing a secret is an explicit operator step.
- The maintenance gate matches `/v1/maintenance` by path prefix (P3: no such
  routes exist, so it is a tidiness issue, not a bypass).

Correctness / coverage:

- SIGKILL in the middle of `restore` has no deterministic injection point; that
  window is reasoned about, not tested.
- Disk-full coverage needs root + tmpfs (Linux CI), not a developer laptop.
- Browser coverage is the 14-test admin core.
- Retention assumes the snapshot directory is operator-owned and private; it does
  not defend against a local attacker who can already write there.
- `retention` orders snapshots by mtime; an operator who rewrites mtimes can change
  which snapshot is considered newest.

## 6. Review status (self-review, independent review pending)

A self-review of `788197a..70ca189` was performed while preparing this freeze. It
found and fixed five real defects, each in its own commit:

1. a committed `.pyc` build artifact (untracked, `__pycache__/` ignored);
2. the maintenance window paused the workflow workers but **not** the 30s deadline
   sweeper, which kept mutating run state while the service claimed to be
   quiesced;
3. the maintenance gate sat outside the rate limiter, so rejected traffic
   bypassed rate limiting;
4. the provenance verifier compared the attestation subject against the index
   digest instead of the platform manifest digest;
5. a verifier flag used by the acceptance script was never registered.

`INDEPENDENT_REVIEW_PENDING` stands. No second reviewer was available in this
session, so this RC may be exercised in a sandbox, but a release decision needs an
independent reviewer to read `788197a..HEAD` with focus on: the materializer
transaction protocol, the maintenance/restore protocol, retention deletion rules,
the provenance verifier, the arm64 acceptance image and the historical replay
harness.

### 10.1 What was fixed

| Finding | Fix | Verified by |
| --- | --- | --- |
| P1-1 journal replay path traversal | `valid_secret_name` enforced on journal write and replay; unknown kind, unsafe name or unverifiable record fails closed; only regular non-symlink backup entries are restored | attack suite 34/34 in CI; the independent reviewer planted its own record, saw rc=1 with the canary intact, and proved the old script deletes it |
| P1-2 retention purge floor | purge refused when nothing verifies or when fewer than `-min-valid` snapshots verify; never below the verified count or the floor; unverifiable reported separately | reviewer CLI probes: nothing verifies gives rc=1 and 0 deleted; a mixed set still prunes above the floor |
| P2-1 name-absent window | live file hard linked into the transaction backup, then replaced by rename | concurrent reader 400 reads with 0 ENOENT; reviewer measured 300/300 against 35 errors on the old code |
| P2-2 silent empty database | `.restore-in-progress` marker before the first rename, cleared on success and on early returns; `storage.Open` refuses to create a database when the marker is present and the database absent | 5 deterministic crash tests including a planted-symlink refusal |
| P2-3 drain missed in-flight Tick | engine counts claimed executing steps, drain waits for them, `ticks_in_flight` is reported | barrier test: drained=false while a step executes, true after it finishes |
| P2-4 stale secret semantics | explicit `--revoke NAME` (charset checked, regular file only, journal `R` record plus hard link, restorable), documented in deploy/secret-materializer/README.md | revoke cases in the attack suite; reviewer reproduced an interrupted revoke being restored |
| P2-5 disk-full could skip | dead flag removed; CI requires `^DISK_FULL_RAN$` under `set -euo pipefail` | CI log shows DISK_FULL_RAN and `SUMMARY pass=33 fail=0 skip=0` |

### 10.4 Additional limitations recorded by the re-verification

- `--revoke` does not suppress the install pass, so revoking a name that is still
  present in `--source-dir` re-installs it in the same run. Remove the name from
  the source projection first. (P2, documentation level, recorded not fixed.)
- If chmod or syncDir fails after the publish, the marker deliberately stays: the
  restore fails closed and the next attempt needs an operator to remove it.
  docs/runbooks/BACKUP-RESTORE.md should mention the marker (P3).
- A revoke-only run prints "materialized 0 secret file(s)" (P3 cosmetic).
- Everything in sections 4 and 5 still stands.
