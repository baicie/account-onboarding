## 2. The DAG fact that decides everything

The 16 open PRs are a chain, and **only #1-#4 target main**:

| PR | head -> base |
| --- | --- |
| #1 | `feat/r8-staging-readiness` -> main |
| #2 | `feat/r9-release-hardening` -> main |
| #3 | `feat/r10-live-preflight` -> main |
| #4 | `feat/r11-integration-readiness` -> main |
| #5..#15 | each -> the previous R-branch |
| #16 | `feat/r22-product-first-final-acceptance` -> `feat/r21-autonomous-final-qualification` |

Therefore **merging PR #16 as currently configured does not put the delivery on
main**: it merges into the R21 feature branch. Anyone clicking "Merge" on #16
today changes a feature branch, not `main`.

Because each branch contains its parent head (`behind=0` everywhere), the stack is
linear, so the delivery reaches main in one step - the question is only how to
express that step.

## 4. Two integration schemes compared (neither executed)

### Scheme A - retarget PR #16's base to main

| Aspect | Assessment |
| --- | --- |
| GitHub allows it | yes, an open PR's base can be changed by someone with write access |
| Resulting diff | becomes `main..feat/r22-...`: 197 commits, 745 files |
| Conflicts | none, proven by the dry run above |
| Reviews | #16 has **0 reviews**, so retargeting loses nothing |
| CI / required checks | main has **no protection and no rulesets**, so no required checks are enforced by GitHub either way; the effective gate would be the workflow-level trusted preflight |
| Effect on the stack | #1-#15 remain open and become stale; their heads are all ancestors of #16, so they can be closed as superseded - but the per-PR audit trail is then only in history, not in merged PR records |
| Risk | a reviewer sees a 745-file diff attached to a PR whose title/description describe only R22 UI work |

### Scheme B - dedicated integration PR from the frozen head to main (recommended)

| Aspect | Assessment |
| --- | --- |
| Mechanics | push a branch at `067e773` (or open the PR from `feat/r22-...` with base main), title it explicitly as "R8-R22 delivery -> main" |
| Resulting diff | identical content to Scheme A (same tree `a132e7c`), but the PR description can carry the full scope, the freeze record and the CI matrix |
| Conflicts | none |
| Reviews | fresh review thread, no inherited approvals |
| CI | same workflows; the trusted preflight set (`ci`, `r12-integration`, `r16-sandbox-e2e`, `r17-browser-e2e`, `supply-chain`, `staging-acceptance`) must be green on the head SHA |
| Effect on the stack | #16 stays Draft and is closed after the integration PR merges; #1-#15 keep their current state |
| Risk | two PRs describe the same content for a short while |

**Recommendation: Scheme B.** It keeps the audited stack intact, makes the review
scope explicit for a 745-file change, and avoids attaching a 197-commit diff to a
PR whose narrative is a single milestone.

## 6. SHA and artifact identity rules

1. The merged (or squashed) commit SHA **will differ** from `067e773`.
2. The tree is unchanged (`a132e7c`), so build inputs are unchanged, but that is
   **not** a licence to reuse anything bound to an old SHA:
   - rebuild the candidate image from the merged SHA;
   - rebind the candidate manifest to the merged SHA, tree, image ID and OCI digest;
   - re-run the preflight against the merged SHA.
3. Any approval, candidate digest, SBOM digest or provenance statement recorded for
   `7f7c3da` / `067e773` is **not** transferable to the merged SHA.
4. `TRUSTED_BUILD_VERIFIED` remains unclaimed: the trusted-preflight verifies CI
   identity, not the build's signature issuer, and the v0.1 provenance work does
   not attest the git source (documented in the freeze record, v0.2 item).

## 7. Required checks - current reality

- `main` has **no branch protection and no rulesets**, so GitHub enforces nothing on a
  merge today. This is the known v0.2 "protected workflow definition" gap, now
  confirmed with fresh API evidence.
- The only enforced gate today is the workflow-level trusted preflight inside
  `release-image.yml`, which requires `ci`, `r12-integration`, `r16-sandbox-e2e`,
  `r17-browser-e2e`, `supply-chain` and `staging-acceptance` to be `push` runs with
  `conclusion=success` on the exact SHA (see `.github/workflows/release-image.yml`,
  "Wait for required workflows on exact SHA").
- Enabling protection with that required set is an **administrator action** and is
  deliberately out of this task. Until then, the operator is the gate.

## 8. Rollback

- Merge commit: `git revert -m 1 <merged-sha>` on main (a squash also reverts as a
  single commit).
- Hard reset of main to `9726fc1` is possible while main is unprotected, but it is a
  history rewrite on the default branch: prefer revert.
- Database: R22 writes schema 6. Rolling the *binary* back to a pre-schema6 build
  against a schema-6 database is not supported - restore the pre-upgrade snapshot
  with the documented maintenance protocol (`docs/runbooks/BACKUP-RESTORE.md`,
  `docs/runbooks/RELEASE_UPGRADE_ROLLBACK.md`) instead of downgrading in place.
