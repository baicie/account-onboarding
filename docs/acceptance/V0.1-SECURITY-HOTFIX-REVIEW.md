## 4. New findings introduced by the fixes

Severity counts: **P0 0 · P1 0 · P2 1 · P3 6.** Nothing here is remotely reachable; there is no unauthenticated path.

### N-1 (P2) — the restore marker follows a symlink: deterministic truncation of an arbitrary file, then the evidence is deleted

`internal/ops/restore.go:375-390` opens the marker with `os.OpenFile(marker, os.O_CREATE\|os.O_TRUNC\|os.O_WRONLY, 0o600)`.
There is no `O_NOFOLLOW` and no `Lstat` refusal, and `clearRestoreMarker` (`:395-401`) then *removes* the path it wrote
through, so the plant disappears.

Reproduced with the shipped binaries (`/tmp/probe_ret/{backup,restore}`, built from HEAD), probe §5.F:

```
before: victim=[IMPORTANT-ROOT-OWNED-CONTENT] size=28
restore_rc=0
after:  victim=[.onboard-restore-408931956.sqlite
2026-10-27T11:14:43Z] size=55
marker_now=GONE              # the symlink was removed, the victim was not restored
target_db=PRESENT           # the restore itself 'succeeded'
```

Who can plant it: whoever may write the directory holding the database — i.e. the service account (the DB, WAL and
this marker all live at predictable names next to each other; `/data` is necessarily writable by the runtime UID).
Who executes it: an operator running `restore` as root, which the runbook already prescribes. Net effect: a
compromised service account can make root truncate an arbitrary path (e.g. `/etc/shadow`, a CA bundle, a config
file), and the symlink is deleted as part of the normal path, so nothing signals it. Content is *not* attacker
controlled (it is the staging temp basename plus an RFC3339 timestamp), so this is a destructive primitive, not code
execution — hence P2, not P1.

Fix is one line: refuse if `os.Lstat(marker)` succeeds (or open with `O_NOFOLLOW`) before writing; and clear the
marker on every early return so a stale plant cannot persist.

### N-2 (P3) — `--require-disk-full` is passed by CI and parsed by nobody

`.github/workflows/r22-deployment-matrix.yml:60` passes `--require-disk-full`, but
`tests/r22/running_restore.sh` contains **0** occurrences of that string, **0** assignments of `REQUIRE_DISK_FULL`,
and no argument-parsing construct at all (`grep -c 'case "$1"\|while \[ "$#"' → 0`). The script also runs without
`set -u`, so the tests at `:179` and `:187` compare an empty string and always take the `skip` branch — simulated:
`REQUIRE_DISK_FULL=[]` → `would-be-skip`. The advertised in-script mechanism is dead code, and an unknown argument is
silently accepted. P2-5 is nevertheless genuinely gated, because the workflow's `grep -q ^DISK_FULL_RAN$` does the
work the flag was supposed to do. Risk is a future caller or a developer running the script by hand getting a SKIP
where they expected a hard failure.

### N-3 (P3) — the revoke semantics are implemented but undocumented and unwired

See P2-4. `deploy/secret-materializer/README.md`: 0 hits for `revoke`; `kubernetes.yaml:17` and the Dockerfile never
pass it. An operator following the deployment contract still has no defined removal procedure.

### N-4 (P3) — residual drain races (narrow, local writes only)

`engine.go:355-368`: `activeTicks.Add(1)` happens *after* `ClaimNext` returns, so a claim that lands in that window is
invisible to a drain that samples there — the original defect, reduced from a whole step execution to a few dozen
instructions. Separately, the 30 s deadline sweeper checks `paused` and then calls `SweepDeadlines`
(`engine.go:224-229`, pre-existing code), so one sweep can begin inside a drain window; it is not counted by
`engineTicks()`. Both write only to the local database, which a restore is about to replace, and neither has an
external side effect. No reproduction attempted (sub-nanosecond timing); this is a code-level residual of the fix,
not a live exploit.

### N-5 (P3) — test seams promoted into the production surface

`internal/api/maintenance_testhook.go:9-11` exports `SetMaintenanceDrainTimeoutForTest`, which mutates the global
drain bound in a normal (non-`_test`) file; `internal/workflow/engine.go:324` `SetTestTickHook` assigns an
unsynchronised field read by every worker (`:369`); `internal/ops/restore.go:373` is an unsynchronised package-level
hook. Nothing in production calls any of them, and `-race` is clean (runs 4 and 5), but a caller that sets the drain
timeout to 0 disables the drain, and the hooks would race if a test ever ran in parallel. Prefer build-tagged files or
a config field.

### N-6 (P3) — the marker is not cleared on the early publish-failure paths, and its content is unhelpful

`restore.go:208` writes the marker; the failure returns at `:225`, `:232` and `:239` (target-aside, WAL-aside, SHM-aside)
return without `clearRestoreMarker`, unlike the later failure path at `:256`. The old database survives those paths, so
`storage.Open` still opens it (`store.go:105` only refuses when the DB is absent). But the stale marker then blocks any
*later* first install of that path until someone removes it by hand. Also cosmetic: the marker records
`filepath.Base(staged)` (`:383`), the random staging temp name, not the snapshot being restored — the operator learns
nothing from it.

### N-7 (P3, pre-existing, related) — the materializer's transaction directory is not anchored

`materialize_secrets.sh:294-297` uses `mkdir -p "$TXNDIR"` and `: >"$JOURNAL"`, both of which follow an existing
symlink. I attempted the same write-through as N-1 and it **did not reproduce**:
`rm -rf -- "$TXNDIR"` at `:202` (inside recovery, which runs first at `:229`) removes the planted symlink before the
journal is opened, so my probe ended with `rc=0` and the victim byte-identical. What remains is a TOCTOU window between
`:229` and `:294` for a writer who does not hold the advisory lock. Recorded for completeness because it shows N-1 is
not an unavoidable consequence of the transaction design — the materializer is protected by accident, the restore
marker has no equivalent step.

## 6. What I did not verify, and why

- **The disk-full path itself.** It needs root on Linux with a mountable tmpfs; this host is darwin/arm64 and
  non-root, and docker/kind/buildx are out of bounds for this review. I verified the *gating* (workflow greps) and that
  the script cannot print `DISK_FULL_RAN` without having attempted the case, not the case's behaviour.
- **CI as a whole.** No workflow run, no push, no PR interaction. My read of `.github/workflows/r22-deployment-matrix.yml`
  is static.
- **`flock(1)` semantics.** See the fidelity caveat in §2; every materializer result ran against my python `fcntl` shim.
- **Hard-link availability on Linux.** The install now needs `ln` where it previously needed only `rename`
  (`:321-323`). On a host with `fs.protected_hardlinks=1` and a materializer UID that does *not* own a 0400 live file,
  `ln` returns EPERM and the run fails closed with `cannot snapshot the live secret into the transaction backup`. The
  shipped deployment runs the init container as root (`deploy/secret-materializer/README.md:69`, `runAsUser: 0`), where
  the sysctl check is bypassed, so I did not rate this; I could not construct the Linux/root scenario here and will not
  claim it as a finding without evidence.
- **Race-window findings (N-4)** were established by reading the ordering, not by winning the race.
- **Restore behaviour on a full filesystem / under kill -9 at other points** — covered by the repository's tests, which I
  ran and inspected, but not re-derived independently.

## 7. Verdict

**HOTFIX_PENDING** — both P1s are genuinely closed and I reproduced the original materializer exploit against the old
script and the original silent-first-install against the current binary; four of the five P2s are closed with tests that
provably fire on a revert; but P2-4 is only partially closed (working `--revoke`, no documented or wired removal
semantics) and this commit introduces one new P2 (N-1: the restore marker follows a symlink and lets a compromised
service account make a root-run restore truncate an arbitrary file, then deletes the evidence).

**What would change it:** refuse a pre-existing/symlinked marker (`O_NOFOLLOW` or an `Lstat` check at
`internal/ops/restore.go:375`) and clear it on the early failure paths (N-1, N-6), plus one paragraph defining `--revoke`
in `deploy/secret-materializer/README.md` (N-3) → **HOTFIX_ACCEPT**. Conversely, if N-1 were reachable without write
access to the database directory, or if attacker-controlled content could be written through it, it would move to P1 and
force **HOTFIX_BLOCK**.
