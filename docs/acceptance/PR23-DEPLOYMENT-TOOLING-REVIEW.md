## P0

- `scripts/update_account_onboarding.sh:548-572` - `ensure_data_owner()` is defined but has no caller: `prepare_deploy()` only verifies owner 10001/mode 0700-0750, while line 94's `mkdir -p` creates `$DATA` as the invoking user (0755) on a fresh host. Reproduced: a fresh `--deploy` exits 2 at `.../runtime/data is owned by 501, not 10001`; the E2E masks this by pre-creating the directory with `sudo install -d -o 10001` at `.github/workflows/deployment-tooling.yml:57`, and the scenario suite only exercises `--deploy --dry-run` (`tests/deploy/update_script_test.sh:128`).
- `scripts/update_account_onboarding.sh:202-203` - `db_file_exists`/`db_file_nonempty` conflate "cannot read" with "absent" (fallback `as_root` at 196-200 returns 1 without passwordless sudo). On the documented 0700:10001 data directory a non-root deployer therefore skips the empty-database check and restore marker (262-267), skips the backup (336-340), and `do_backup` even reports success via `! db_file_exists` (476), while `do_deploy` continues at 485. Reproduced: `--preflight` returned 0 with an empty `state.sqlite` in an unreadable data dir, and `--backup-only` returned 0 with "no database to back up" while a database existed. This defeats the stated empty-DB/restore-marker/snapshot guarantees.

## P1

- `scripts/update_account_onboarding.sh:178` - the generated override adds `127.0.0.1:$HOST_PORT:8788`, but the base file already publishes `127.0.0.1:8788:8788` (`deploy/compose.yaml:65`). Compose merges service `ports` by `{ip,target,published,protocol}`, so a different published port is appended, not replaced: `--host-port=18788` leaves 8788 bound too. `--status` (544) and `--rollback` (522/528) ignore the recorded `host_port` (393) and fall back to 8788; the E2E uses `--host-port=18788` at `.github/workflows/deployment-tooling.yml:67` but probes 8788 in the status/rollback steps (72, 106, 112), so those assertions pass against the base port without proving the configured port.
- `scripts/deploy/README.md:45` - the documented `runtime/secrets-src` layout is 0444, and `.github/workflows/deployment-tooling.yml:60` enforces `chmod 0444`. `api_probe` reads the admin token from that path (412), so any local user who can traverse the 0755 runtime directory can read the master key and admin token, defeating the 0400 materialized-secret contract. The source only needs to be readable by the deploy user (e.g. 0400 owned by that user).
- `scripts/update_account_onboarding.sh:495-502` - state is written only after health succeeds. If a deploy fails `wait_healthy`, the state still describes the pre-deploy image; `do_rollback` reads `previous_image` (510-512), not the image currently running or the just-recorded `image`. After a first deploy the recorded previous image is empty, so the advertised recovery at 498 (`--rollback`) fails with "no previous image recorded"; after later deploys it rolls back one generation too far.

## P2

- `scripts/update_account_onboarding.sh:317-320` - materialized-secret verification only checks that `/$f` exists via `ls -l` and accepts mode `400|600`; it does not verify "regular file" or owner 10001, and `stat` follows symlinks. This is weaker than README:36's "0400 ... owned by 10001" claim.
- `scripts/update_account_onboarding.sh:168,523-524` - `--dry-run` is not side-effect free: `write_overrides` does `cp "$APP/deploy/compose.yaml"` before its dry-run check, `do_rollback` still calls `compose_valid` and `materialize_secrets` (whose `dk run` checks at 317/319 are outside `run`), and `--backup-only --dry-run` dies 3 at 476 ("no usable snapshot") after printing "DRY-RUN would snapshot" (reproduced).
- `scripts/update_account_onboarding.sh:333` - `sh -ec "... /out/ops-$tool $*"` interpolates arguments into a shell command string; an argument with whitespace or shell metacharacters will break or inject. Use positional `"$@"`.
- `scripts/update_account_onboarding.sh:87,256-260` - only `$ROOT` itself is checked for being a symlink; `$APP`, `$SECRETS`, `$BACKUPS`, `$DEPLOY`, `$LOGS`, and `state.sqlite-wal/-shm` are not checked. `do_rollback` (506) and `do_backup` (473) never run `check_data_safety`, so the data-dir symlink and restore-marker checks are bypassed on those paths.
- `scripts/update_account_onboarding.sh:517` - the rollback schema guard only runs when `previous_schema_version` is non-empty; a state file lacking that key skips the guard, while the always-written `0` value blocks every rollback. `state_num` (403) cannot distinguish missing from zero.
- `scripts/update_account_onboarding.sh:178,393` - `--host-port` is never validated numeric and is printf'd unquoted into the override YAML and state JSON; malformed values can corrupt the generated files (same class applies to YAML interpolation of `$DATA`/`$SECRETS`).
- `scripts/update_account_onboarding.sh:167` - copying `$APP/deploy/compose.yaml` to `$DEPLOY/compose.base.yml` changes the base's relative `build.context: ..` (`deploy/compose.yaml:25`) from `$APP` to `$ROOT`; `--no-build` hides this, but `docker compose config`/`build` against the generated base resolves the wrong Dockerfile context.
- `scripts/update_account_onboarding.sh:523` - `--rollback` changes the running binary without taking the encrypted snapshot that README:34 promises for "every state change"; the rollback path never calls `take_backup`.
- `.github/workflows/deployment-tooling.yml:178` - cleanup runs `docker compose -p account-onboarding down --remove-orphans` with neither `-f` nor the generated base/override; the repo root has no default compose file (only `deploy/compose.yaml`), so this can fail with "no configuration file provided" or target an unrelated root stack. Line 166 also logs `docker logs account-onboarding`, but the compose container is `account-onboarding-onboarding-1`; the `|| true` group silently drops the evidence.
- `tests/deploy/update_script_test.sh:87,128` - the fixture creates `$ROOT/runtime/data` as the invoking user (0755) and only tests `--deploy --dry-run`; there is no non-dry first install, successful rollback, successful backup, host-port, or unreadable-data-dir case, which is why the P0 defects pass the suite.
- `scripts/deploy/README.md:34,36` - docs claim every state change is preceded by a verified snapshot and secrets are 0400, while rollback takes no snapshot and the verifier accepts 0600; README:31 also presents offline mode as using exactly the pinned commit, but Docker builds and `ops_run` still use network/GOPROXY (`scripts/update_account_onboarding.sh:331-333,373`). Runbook additions repeat the first-install/E2E claims at `docs/runbooks/DEPLOYMENT.md:13-16,32-34` and `docs/runbooks/RELEASE_UPGRADE_ROLLBACK.md:95-98,114-116`.
- `scripts/update_account_onboarding.sh:105,539` - `detect_docker` validates `docker compose version` with plain `docker` even when access was established through `sudo -n docker`, so sudo-only hosts are told the compose plugin is missing; `do_status`'s `detect_docker 2>/dev/null || { ... }` fallback is unreachable because `detect_docker` calls `die` (exits).
