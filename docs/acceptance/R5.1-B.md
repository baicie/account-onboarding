## 2. 审计中发现的代码缺口与修复（真实可复现）

本轮在“审计 Dockerfile/Compose/健康检查/密钥路径”时发现两个会影响容器运行正确性的
**可复现**问题，按“先写回归测试再最小修复”处理：

### 2.1 文档声称支持的 JSON keyring 实际被拒绝（**已修复**）

- 现象：`deploy/secrets/onboarding_master_key.example` 与 `config` 注释均声明支持
  `{"current":1,"keys":{"1":"<base64<32B>>"}}`，但 `config.DecodeMasterKey` 只接受
  raw/hex/base64，JSON 文件会导致容器启动失败（本地实测：`master key must be 32 bytes ...`）。
- 修复：`internal/config/config.go` 新增 `decodeKeyringEnvelope`，解析 `current` 版本对应的
  32 字节 key；格式错误的 JSON/缺失版本/metadata 失败关闭，不再回落为 raw。
- 回归：`TestDecodeMasterKeyJSONKeyring`（含 4 个负向样例）+
  `TestDecodeMasterKeyRawKeyStartingWithBrace`（raw 32B key 即使以 `{` 开头也不得被 JSON 探测吞掉）。
- 端到端证据（无 Docker）：`tests/r51/healthcheck_evidence.sh` → **6/6 PASS**
  （JSON keyring 启动、`/readyz` 200、healthcheck 0、缺失撤销表 → `/readyz` 503、healthcheck 1、
  raw 32B key 仍可用）；日志：`evidence/R5.1-B-healthcheck.log`。

### 2.2 Docker `HEALTHCHECK` 只探测 HTTP 端口（**已修复**）

- 现象：`onboardd healthcheck` 只 GET `/healthz`（liveness），数据库损坏、schema 不对、
  撤销表缺失时仍可能报告 healthy —— 不满足“健康检查必须真正检测数据库与运行状态”。
- 修复：`healthcheck` 改为加载配置并调用**认证的 `/readyz`**（检查 WAL、schema≥3、
  `session_revocations` 表、master key、写能力）；失败时退出非零，且不打印 token/响应体。
  容器内 HEALTHCHECK 命令不变（`/app/onboardd healthcheck`），语义变严格：**需要完整配置与
  admin/readonly token**（Dockerfile 的 HEALTHCHECK/compose 已提供 secret 挂载；纯 liveness 探针应直接
  使用 `/healthz`，不要再把旧版 healthcheck 当无认证探针）。Dockerfile HEALTHCHECK 增加 `--start-period=10s`。
- 回归：`cmd/onboardd/healthcheck_test.go`（有效/无效 token、503、不可达、错误不泄漏 token）。
- 证据：同上日志；degraded DB 时 healthcheck **exit 1**。

### 2.4 容器 Secret 可读性审计（静态发现的高风险部署项，待容器验证）

容器最终以 **UID 10001** 运行；若 secret 以 host bind mount 方式提供且文件属主是部署用户、
权限 0400/0600，容器内 10001 通常**无法读取**，服务会启动失败。这一点在无 Docker 环境下
无法实测，但代码/Compose/脚本审计已暴露风险：

- `deploy/scripts/preflight.sh` 现在在 secret 属主既不是 10001 也不是 root 时给出
  **可操作 warning**（建议 Linux 上 `chown 10001:10001`，或验证 Compose secret 的 ownership 映射）；
- `tests/r51/docker_acceptance.sh` 将显式断言：
  手动容器内 `test -r /run/secrets/onboarding_master_key` 与 admin token 均可读，
  且 mode 无 group/other 写位；Compose 段同样检查 `/run/secrets/*` 对 10001 可读，
  失败会以 `FAIL compose secrets not readable by UID 10001` 暴露（不会静默通过）。
- 该风险与 `R4 P1-5 / R5.1-B` 部署前置相关：生产必须保证 secret 对 10001 可读（owner 或 uid/gid 映射），
  不能只满足"0400/0600"。

### 2.5 回归验证

- `make verify` → **0**；`go test ./... -race` → **0**；
- `go test ./cmd/onboardd/ ./internal/config/` → **0**（新增 4 个顶层测试）；
- 这两项修复不改动 R0–R5.1 的既有行为（仅新增格式支持与更严格的健康检查）。
